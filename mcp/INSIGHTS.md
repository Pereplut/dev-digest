### 2026-09-27 — [dep] `toNodeHandler` lives in `@modelcontextprotocol/node`, not `@modelcontextprotocol/fastify`
**Context:** wiring `entry/http.ts` per spec 0011, which names only `@modelcontextprotocol/server` and `@modelcontextprotocol/fastify` in its stack table.
**Insight:** `@modelcontextprotocol/fastify@2.0.0` exports only `createMcpFastifyApp`/`hostHeaderValidation`/`originValidation` — no Node request adapter. The `(req, res, parsedBody?)` wrapper the spec's mounting hazards describe is `toNodeHandler` from a third package, `@modelcontextprotocol/node@2.1.0`, whose only extra runtime dependency is `@hono/node-server` (its `hono` peer is optional and unneeded for `toNodeHandler` alone).
**Apply:** when wiring `createMcpHandler`'s web-standard handler into any Node HTTP framework (Fastify, Express, plain `node:http`), add `@modelcontextprotocol/node` explicitly — `@modelcontextprotocol/fastify` alone is not enough.
**Evidence:** `mcp/src/entry/http.ts:24` (the import); `node_modules/@modelcontextprotocol/fastify/dist/index.d.mts` exports list (no `toNodeHandler`); `node_modules/@modelcontextprotocol/node/dist/index.d.mts:260` (`declare function toNodeHandler`).

### 2026-09-27 — [dep] `GET /runs/:id/findings` carries only its own run's status — no pull id, no sibling runs
**Context:** the server agent building the new route confirmed its shape from `server/src/vendor/shared/contracts/findings.ts` while this package's `registry.ts` was mid-implementation against spec 0011's single verbatim "still executing" text (`"...status: running, 2 of 3 agents done)..."`).
**Insight:** the confirmed `RunFindingsPage` is `{ findings, status, next_cursor }` — flat, with no `pull_id`/`agent_id`/sibling-run data. The "N of M agents done" clause is undeliverable from a bare `run_id`; it is only computable when `get_findings` was called with `repo`+`pull_number`, because only then is the pull id known and `GET /pulls/:id/runs` (already existing) can be counted.
**Apply:** `runStillExecutingText` takes a two-variant `StillRunningInfo` (`mode: 'run'` omits the clause, `mode: 'pull'` includes it) rather than one shape — don't assume a spec's single example string is reachable from every call path that triggers it; check what the concrete route actually returns first.
**Evidence:** `mcp/src/core/errors.ts:21-36` (`StillRunningInfo`, `runStillExecutingText`); `mcp/src/tools/findings.ts:66-82` (the `listRunsForPull` batch-counting branch, `pull` mode only).

### 2026-09-27 — [odd] An array-only enum param makes the tool stricter than the route it wraps, and the model pays a turn for it
**Context:** live-calling `get_findings` against the running API with `severity=CRITICAL`. It failed: `Input validation error: … severity: Invalid input: expected array, received string`. The same filter on the HTTP route it wraps works with a bare scalar.
**Insight:** `severity`/`category`/`status` were `z.array(z.enum(...))`, while `RunFindingsQuery` on the API side is `z.union([Scalar, z.array(Scalar)]).transform(toArray)`. So the MCP tool rejected a spelling its own backend accepts. `severity: "CRITICAL"` is the natural way to write a single filter, and the trap is self-baited: the stub's own error text reads `get_findings (severity: ["CRITICAL"])`, so the array form is the only one a model ever sees demonstrated. Unit tests could not catch it — they all passed arrays, which is the shape that already worked.
**Apply:** when a tool wraps an HTTP endpoint, make its schema no stricter than that endpoint's — mirror the union rather than tightening it. More generally, a tool schema that only ever gets exercised with the shape you had in mind is untested for the shape a model will actually send; call it over the wire with the obvious wrong spelling before believing the tests.
**Evidence:** `mcp/src/registry.ts` (`oneOrMany`, and its three call sites in `GetFindingsInput`/`GetRepoConventionsInput`); `server/src/vendor/shared/contracts/findings.ts` (`RunFindingsQuery`'s union); regression test `mcp/test/registry.test.ts` ("a scalar severity filters the same as a one-element array").

### 2026-09-27 — [measured] The five tool definitions are 1,446 tokens — the pre-implementation estimate was 2.4x too high
**Context:** spec 0011 asserted "roughly 2.5–3.5k tokens", written before any schema existed, and the budget test's ceiling had been derived from that upper bound (4,000).
**Insight:** measured with `js-tiktoken` `cl100k_base` over the real `tools/list` output: **1,446 tokens** / 6,310 chars (`get_findings` 1,925 chars is the largest, `get_blast_radius` 741 the smallest). A 4,000 ceiling against a 1,446 actual means the definitions could nearly triple — a sixth tool, or a re-introduced `outputSchema` — without the test firing. Ceiling is now 2,000 (~38% headroom) with a lower bound at 75% of measured, so a registry that silently registers fewer tools fails too.
**Apply:** never derive a budget assertion from a pre-implementation estimate; measure first, then set the bound from the measurement. A ceiling with 3x slack is the "ruleset that never fails" failure mode the `onion-architecture` skill warns about, in test form. Guard both directions — a ceiling-only assertion passes when content goes missing.
**Evidence:** `mcp/test/token-budget.test.ts` (`TOKEN_CEILING = 2000`, `MEASURED_AT_WRITING = 1446`, and the both-directions assertions).

### 2026-09-27 — [tool] The Inspector CLI does not pass the shell's env to the server it spawns — `-e` is the only way
**Context:** testing the "API unreachable" path with `DEVDIGEST_API_BASE=http://localhost:39999 npx @modelcontextprotocol/inspector --cli … --tool-name list_review_agents`. It returned five real agents from the live API on :3001 instead of the unreachable error.
**Insight:** the prefixed variable never reaches the child: the Inspector spawns the stdio server with its own environment, so `buildApi` fell back to `DEFAULT_API_BASE`. `DEVDIGEST_MCP_MOCK=1` is silently ignored the same way — a run "verified against the mock" through a shell prefix is actually hitting the real API, and the output looks plausible enough not to notice (real agent uuids, not the mock's `agent-1`). The flag is `-e KEY=VALUE`, placed before `--method`; with it the same call returns the correct `Cannot reach the DevDigest API at http://localhost:39999…`. Proven independently: `buildApi({DEVDIGEST_API_BASE:…})` and `new HttpDevDigestApi({baseUrl:…})` both honour their input, so the product was never at fault.
**Apply:** always pass env to the Inspector with `-e`, never a shell prefix, and make the assertion something the two modes cannot both satisfy (mock ids differ from live ids — check for `agent-1`, don't eyeball "looks like mock data"). Any past claim of the form "verified through the Inspector with ENV=x" is worth re-running.
**Evidence:** `npx @modelcontextprotocol/inspector@2 --cli --help` (`-e <env>  Environment variables for the server (KEY=VALUE)`); `mcp/src/container.ts:13-19` (`buildApi(env = process.env)`); `mcp/src/adapters/http/client.ts` (`DEFAULT_API_BASE` fallback).

### 2026-09-27 — [fix] A 404 from the API surfaced as a bare "Run not found" — the one error shape with no next action
**Context:** calling `get_findings` with an unknown run id against the live API. Five of the six spec'd error texts name a recovery; this one printed three words.
**Insight:** `apiErrorText` returned `body.error.message` unchanged, and the API's messages are written for a developer reading a log, not a model deciding what to do next. The spec's six verbatim texts never enumerated "unknown id", so nothing caught it — no test failed, because the test asserted exactly the pass-through behaviour that was the bug. Fixing it also exposed a type-level lie: `apiErrorText(body: ApiErrorLike)` was being handed `{code: String(err.status)}` by its only call site, stuffing an HTTP status into a field contractually holding the API's semantic code (`invalid_run_request`, `invalid_cursor`, …). Status is now a separate parameter and the hint switches on it.
**Apply:** when a tool proxies an API, treat the API's own error strings as raw material, not as tool output — append the recovery per status class (404 → where ids come from, 429 → which limit, 5xx → retry is reasonable, unknown → add nothing). And when a helper's parameter is typed as one vocabulary but only ever receives another, split the parameter rather than widening the type.
**Evidence:** `mcp/src/core/errors.ts` (`apiErrorText(status, body, fallback)` and `recoveryHint(status)`, with the comment on why it is not keyed on `error.code`); `mcp/src/registry.ts` (the single call site, now `apiErrorText(err.status, err.body, err.message)`); `mcp/test/core/errors.test.ts` (`describe('apiErrorText — every status class names a recovery')`).

### 2026-09-27 — [odd] `findings: []` on a `done` run means two opposite things, and only `grounding` tells them apart
**Context:** ran `review_pull_request` on the seeded `acme/payments-api#482`. The run completed in 4s, spent 3185 in / 231 out tokens and $0.000489, and returned zero findings.
**Insight:** zero findings was not a clean bill of health — all four of that PR's `pr_files` rows carry `patch = NULL` (the repo has `clone_path: null`, so it was never cloned), and the agent was handed no diff at all. The run row's `grounding` read `0/0 passed`; a genuine review of the same shape reads `11/11 passed` (verified on `Pereplut/dev-digest#6`). `status` alone cannot separate the two, so any consumer reports "no issues found" for a review that examined nothing. `grounding` now travels with `status` through `GET /runs/:id/findings` and out of `get_findings`.
**Apply:** never treat an empty findings list as "clean" without checking `grounding` — `0/0` means nothing was examined. It is omitted in the `repo`+`pull_number` path on purpose: grounding is per-run, and that path merges the latest review of every agent, so one run's tally would misdescribe the rest.
**Evidence:** `server/src/modules/reviews/repository/review.repo.ts` (`grounding` selected beside `status`, with the reason); `server/src/vendor/shared/contracts/findings.ts` (`RunFindingsPage.grounding`); `mcp/src/tools/findings.ts` (pull path returns `grounding: null`); live: run `9e865e64` → `0/0 passed`, run `1e0670f4` → `11/11 passed`.

### 2026-09-27 — [fix] "N of M agents done" counted historical runs, then counted them wrong twice over
**Context:** started a 4-agent review on `Pereplut/dev-digest#6` and polled by `repo`+`pull_number`. The message read `0 of 5 agents done`.
**Insight:** three distinct bugs, each only visible against real data. (1) The tally took the latest run per agent keyed on `agentId ?? runId` — a `failed` run from nine days earlier whose agent had since been DELETED has `agentId: null`, so it keyed on its own run id and survived as its own pseudo-agent. M was 5 for a 4-agent review, and being terminal it could never finish, so the count would top out at 4 of 5 and read as permanently stuck. (2) Anchoring the wave on the oldest still-RUNNING run then dropped the wave's earliest agent the moment it completed: `1 of 4` rendered as `0 of 3`, the denominator shrinking as work finished. (3) Deciding "no wave" from missing timestamps rather than from "is anything running" served results mid-review — caught by a test written for the fix, not by the live run.
**Apply:** a wave is a time cluster, not a status filter: `review_pull_request` creates all its `agent_runs` rows in one loop (timestamps 723/727/730/732 ms apart), separate reviews are minutes or days apart, so walk newest-first and cut at the first gap over 60s. And when reconstructing a batch the API does not identify, treat "which runs are mine" as its own pure function with its own tests — the arithmetic on top of it is where the errors hide.
**Evidence:** `mcp/src/core/project.ts` (`currentWave`, `WAVE_GAP_MS`); `mcp/src/tools/findings.ts` (the single call site replacing the latest-per-agent map); `mcp/test/core/project.test.ts` (`describe('currentWave …')`, four cases from the live data); live sequence: `0 of 5` → `0 of 3` → `1 of 4`.

### 2026-09-27 — [dep] The MCP SDK's JSON-Schema conversion silently drops `examples` from any object containing a transform
**Context:** `/pr-self-review` flagged that `get_findings`'s advertised example `run_id: 'run_abc123'` no longer satisfied the `.uuid()` just added to that field. Fixing the value led to a test asserting every published example round-trips — which then found that `get_findings` was publishing **no** examples at all, although its `.meta({ examples })` looked identical to `review_pull_request`'s, which does publish.
**Insight:** the conversion the SDK actually performs is `schema['~standard'].jsonSchema.input({target:'draft-2020-12'})` — **not** `z.toJSONSchema`, which is only a fallback behind a `console.warn` for zod < 4.2. Grepping for `toJSONSchema` will not find the live call. Either way the behaviour is the same and it is silent: **`examples` is dropped from every object that has a transform anywhere below it**, at any depth, so nesting the transform-bearing fields deeper does not rescue an object-level example; a sibling object without a transform keeps its own. `oneOrMany` (the scalar-or-array helper on `severity`/`category`/`status`) is a `ZodPipe`, so `get_findings` and `get_repo_conventions` were both affected and `review_pull_request` was not. Three things narrow the rule: only `examples` is affected — `title` and `description` on the same object survive; `.meta({examples})` on the transform field **itself** is dropped too, so the scalar-vs-array spelling can only ever be shown in `.describe()` text; and with `{io:'output'}` the same call **throws** `Transforms cannot be represented in JSON Schema`, so the failure mode depends entirely on direction — one errors, the one in use swallows. There is no better workaround: `{io:'output', unrepresentable:'any'}` keeps root `examples` but erases each transform field to `{}` (losing `severity`'s enum), and the conversion call belongs to the SDK, so neither that nor the `override` hook is reachable from this package. Field-level `examples` is the answer, and `.describe()` before `.meta()` keeps both.
**Apply:** put `examples` on the FIELD in any schema using `oneOrMany` or another transform, and never treat "it compiles and `tools/list` succeeds" as evidence that metadata reached the client — assert publication in a test, reading `tools/list` back, because the drop is silent at every layer. Zod 4 also enforces RFC 9562 for `z.uuid()` (version nibble 1-8, variant 8/9/a/b), so `11111111-1111-1111-1111-111111111111` fails while `11111111-1111-4111-8111-111111111111` passes.
**Evidence:** `node_modules/@modelcontextprotocol/server/dist/src-D-y6h4N7.mjs:5369-5383` (`standardSchemaToJsonSchema`, the live path and its warned fallback); `mcp/src/registry.ts` (the field-level example on `run_id`, and the comment on `GetFindingsInput` recording why it carries no object-level `.meta`); `mcp/test/registry.test.ts` (`describe('input examples are valid against their own schemas')`, asserting validity AND publication); `node_modules/zod/v4/core/regexes.js:27` (the RFC 9562 pattern), `node_modules/zod/v4/classic/schemas.d.ts:123` (`@deprecated Use z.uuid() instead`).

### 2026-09-27 — [fix] `encodeURIComponent` cannot neutralise a `..` path segment
**Context:** the round-1 fix for an unencoded-path-segment WARNING added a `seg()` helper whose docstring claimed "a segment can no longer break out of its position". Round 2 of the same review pointed out that this is false.
**Insight:** `encodeURIComponent('..') === '..'` — there is nothing in a dot-segment to escape, so WHATWG normalisation still removes the preceding path level and `/repos/../pulls/42` resolves to the real `GET /pulls/:id`. The round-1 regression tests covered `/`, `?` and `=` and therefore pinned every case except the one the docstring's claim depended on. Not reachable today (`run_id` is `z.uuid()` and every other segment is an id the API itself returned), so it was graded SUGGESTION — but the docstring was asserting an invariant the code did not hold.
**Apply:** a path-segment encoder has to REJECT `''`, `'.'` and `'..'`, not encode them; encoding is necessary and not sufficient. And when a fix's docstring states an invariant, the test list is what makes it true — check that the claim and the cases match, because an overclaiming comment is worse than none.
Second round of the same review found the guard still had a hole: the parameter is typed `string`, but two call sites pass `repo.id`, which comes from a blind `(await res.json()) as T`. A `/repos` row without an `id` is `undefined` at runtime while still typed `string`, the value-equality checks miss it, and `encodeURIComponent(undefined)` returns the literal `"undefined"` — so `GET /repos/undefined/pulls/42`. **A guard written against a declared type does not defend the runtime value when that type came from a cast**; the `typeof` clause is the load-bearing one, not belt-and-braces.
**Evidence:** `mcp/src/adapters/http/index.ts` (`seg()` rejects a non-string plus the three unfixable values, with the corrected docstring claim); `mcp/test/adapters/http.test.ts` (`it.each(['..', '.', ''])`, asserting `fetch` is never called).

### 2026-09-28 — [measured] Wiring `get_blast_radius` into a real tool moved the token budget from 1446 to 1668
**Context:** spec 0012 replaced the stub body (`isError: true`, one short line, no port call) with a real description (§6, four sentences) and a real handler. `token-budget.test.ts`'s `MEASURED_AT_WRITING` still held the spec-0011 figure.
**Insight:** re-measured with the same `js-tiktoken` `cl100k_base` method over live `tools/list` output: **1668** tokens total (`get_blast_radius` alone: 266, up from a one-line stub). `TOKEN_CEILING` stays 2000 per spec 0012 §5's explicit instruction not to nudge it — now ~20% headroom instead of the ~38% spec 0011 left, tighter but still passing both directions of the test.
**Apply:** any future tool whose description grows (a stub becoming real, a parameter added) needs `MEASURED_AT_WRITING` re-measured and the *remaining headroom*, not just the ceiling, checked against what is still planned — the margin does not reset itself and it can quietly run out.
**Evidence:** `mcp/test/token-budget.test.ts` (`MEASURED_AT_WRITING = 1668`); measured per-tool via `tools/list` + `getEncoding('cl100k_base').encode(JSON.stringify(tool)).length`.

### 2026-09-28 — [dep] `get_blast_radius` has no `response_format` param, so its ring-1 projection takes no `format` argument either
**Context:** spec 0012 §5 describes `projectBlast(...)` as "following the `projectFinding`/`projectConvention` pair shape" — both of those take a `ResponseFormat` and branch concise-vs-detailed. `GetBlastRadiusInput` (registry.ts, frozen by the same spec) has only `repo` and `pull_number` — no `response_format`.
**Insight:** the map is already the concise shape — the route's whole point is "callers, endpoints, crons", with no larger form to gate behind a `detailed` flag — so `projectBlast(result: BlastRadiusResult): BlastRadiusProjection` takes one argument, not two. The "build a concise base object, then conditionally spread extra fields" *shape* still applies: the condition is `result.degraded !== undefined`, not a caller-supplied format.
**Apply:** when a spec says "follow the X/Y projection shape" for a tool whose input schema has no `response_format`, read that as the code *pattern* (base object + conditional spread) rather than a literal second parameter — check the frozen input schema first, don't assume every projection takes a format.
**Evidence:** `mcp/src/core/project.ts` (`projectBlast`, one-argument signature); `mcp/src/registry.ts` (`GetBlastRadiusInput`, no `response_format` field).

### 2026-09-28 — [dep] `token-budget.test.ts` bounds the tool SCHEMA, not any tool's result payload — a ring-1 projection change doesn't move it
**Context:** added a downstream-group cap (`MAX_BLAST_DOWNSTREAM_GROUPS`) inside `projectBlast` (spec 0012 post-review) and had to decide whether `MEASURED_AT_WRITING` needed re-measuring, per the spec's own "never nudge the ceiling to fit" rule.
**Insight:** `token-budget.test.ts` serialises `client.listTools()` — the `tools/list` response built from `registry.ts`'s Zod schemas/descriptions — never a `tools/call` result. Changing what `projectBlast` returns (in `core/project.ts`, ring 1) leaves that serialisation byte-for-byte identical as long as `registry.ts` itself (description, input schema, annotations) is untouched. Re-ran the suite unchanged and confirmed `1668` still holds.
**Apply:** when a change only touches a ring-1 projection function's *output shape* and not a tool's registered description/schema, `token-budget.test.ts` needs no re-measurement — grep the diff for `registry.ts` before assuming otherwise; only a description/schema edit moves that number.
**Evidence:** `mcp/test/token-budget.test.ts:35` (`client.listTools()`, not `callTool`); `mcp/src/core/project.ts` (`projectBlast`'s trimming, no `registry.ts` change); `npm test` re-run this pass: `token budget — serialised tool definitions > tools/list output stays under the recorded ceiling` still passes at `MEASURED_AT_WRITING = 1668`.
